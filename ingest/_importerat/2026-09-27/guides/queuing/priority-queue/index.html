Priority Queue

A queuing system where items are served in priority order rather than arrival order. High-priority items jump ahead of lower-priority items in the queue, modeling emergency services, VIP lanes, or job scheduling with urgency levels.

When to use this

  • Modeling systems where certain customers or jobs must be served before others regardless of arrival order
  • Evaluating the impact of priority classes on wait time distribution across customer segments
  • Modeling preemptive or non-preemptive service disciplines in computer or manufacturing systems
  • Designing triage systems in healthcare, emergency response, or critical systems
  • Analyzing fairness trade-offs: high-priority items get fast service but low-priority items may wait excessively

Blocks

BlockLibraryLabelPurpose
CreateItem.lbrArrivalsGenerates all arriving items; may use multiple Create blocks for different priority classes
SetItem.lbrAssignPriorityAssigns a numeric priority attribute value to each item (e.g., 1=high, 3=low); attribute name must match Queue sort attribute
QueueItem.lbrPriorityQueueRanks waiting items by attribute value; lower attribute value = higher priority when ascending sort is used
ActivityItem.lbrServerProcesses items one at a time; always takes the highest-priority item from the Queue
ExitItem.lbrDeparturesCollects items and records statistics; add separate Exit blocks per priority class for segmented analysis

Connections

  • Arrivals (ItemOut) → AssignPriority (ItemIn)
  • AssignPriority (ItemOut) → PriorityQueue (ItemIn)
  • PriorityQueue (ItemOut) → Server (ItemIn)
  • Server (ItemOut) → Departures (ItemIn)

Common mistakes

  • Setting the Queue sort attribute name that does not exactly match the attribute name assigned by the Set block — the Queue will not recognize the attribute and will default to FIFO, silently ignoring priorities; attribute names are case-sensitive
  • Using ascending sort with higher numbers meaning higher priority — this sorts backwards; either use lower numbers for higher priority with ascending=true, or use descending=true with higher numbers for higher priority
  • Using a single Create block and trying to assign priorities probabilistically inside one Set block — it is cleaner and more accurate to use separate Create blocks with different rates for each priority class so arrival rates are independently controlled
  • Omitting the Set block and trying to assign priority in the Create block itself — Create block does not support attribute assignment; a Set block immediately after Create is required

What to measure

  • Average wait time per priority class (use separate Exit blocks or attribute-filtered statistics)
  • Queue length breakdown by priority level
  • Server utilization (shared across all priority classes)
  • Probability low-priority items wait longer than acceptable threshold
  • Throughput per priority class versus arrival rate
