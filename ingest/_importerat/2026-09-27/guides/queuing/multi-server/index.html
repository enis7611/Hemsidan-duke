Multi-Server Queue (M/M/c)

A queuing system with multiple parallel servers sharing a single waiting line. Items wait in one queue and are routed to the next available server, modeling call centers, bank teller lines, or parallel machines.

When to use this

  • Modeling multiple identical servers serving one shared waiting line (e.g., bank tellers, checkout lanes)
  • Finding the optimal number of servers to balance cost against customer wait time
  • Comparing single-queue/multi-server versus multi-queue/single-server configurations
  • Evaluating the impact of adding or removing servers on throughput and utilization
  • Modeling parallel machines or workstations in a manufacturing cell

Blocks

BlockLibraryLabelPurpose
CreateItem.lbrArrivalsGenerates arriving items according to inter-arrival distribution
QueueItem.lbrSharedQueueSingle shared waiting line for all servers; items leave when any server becomes free
WorkstationItem.lbrServersMulti-server processing block with built-in queue and configurable maxServers parameter; simplest approach for M/M/c
ExitItem.lbrDeparturesCollects completed items and records throughput statistics

Connections

  • Arrivals (ItemOut) → Servers (ItemIn)
  • Servers (ItemOut) → Departures (ItemIn)

Key parameters

BlockParameterTypicalWhat it controls
WorkstationmaxServers2-5Number of parallel server channels. This is the 'c' in M/M/c. The Workstation block includes its own internal queue, so no separate Queue block is needed when using Workstation.
Workstationdistribution / arg1Exponential, mean=8 minService time distribution per server. Each server independently samples from this distribution.
Createdistribution / arg1Exponential, mean=3 minInter-arrival time. Total offered load = mean service time / (c * mean inter-arrival time) must be < 1.
WorkstationmaxQueueLength0 (unlimited)Maximum internal queue capacity. Set to 0 for unlimited. When queue is full, new arrivals are blocked.

Common mistakes

  • Using a Workstation block (which has an internal queue) and also placing a separate Queue block before it — this creates two queues in series, inflating wait times and misrepresenting system behavior; use Workstation alone or use separate Queue+Activity blocks
  • Setting maxServers on a Workstation but forgetting that Workstation service time is per item, not shared across servers — each server independently draws from the service distribution
  • Connecting parallel Activity blocks without Select Item Out/In routing — items will only flow to the first connected Activity; use Select Item Out (shortest queue mode) to distribute load correctly when using separate Activity blocks instead of Workstation
  • Not verifying offered load (lambda / (c * mu)) is below 1.0 — with multiple servers the stability condition is different from M/M/1 and is easy to miscalculate

What to measure

  • Average number waiting in queue (Workstation internal queue statistics)
  • Average wait time before service begins
  • Individual server utilization (should be balanced across servers)
  • Overall throughput versus arrival rate
  • Probability that all servers are busy (P(delay))
